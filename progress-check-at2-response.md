# AIF AT2 — Progress Check Response

Project: **Kobald** (formerly Project JARVIS) — a governed autonomous AI system for research and authorised security work.

My learning goal is to design, build and safely operate Kobald around one principle: *autonomous in thought, cautious in action*. This check covers early July to late August, in which the core grew to roughly 54,000 lines across 102 modules, backed by about 2,110 tests.

## PA2 — Managing time and resources

I manage time in numbered phases of small, dated commits, so progress is measurable and a bad week cannot erase a good one — my busiest day (16 commits) came from batching small verified steps. The resources I have used are deliberately few: the Python standard library for the core (so every line is auditable), local Ollama models plus two consent-gated cloud models, systemd, Tailscale, an isolated worker VM behind a kill-switch VPN, GitHub Actions for Windows builds, a desktop client, and AI assistants as pair-programmers and hostile reviewers. Next I will need a second machine for peer testing and an external reviewer.

The biggest risk in my learning is that a mistake here is not just a mark lost — this code can take real actions, so a double-fired command or a leaked token is a genuine hazard. I manage that risk by making safety structural: a default-deny policy engine (WARDEN) pauses every state-changing action for human approval, task state is HMAC-sealed and fails closed on tampering, and deployments back up before copying. When live feed ingestion broke on claim-length caps and dotted ATT&CK identifiers, I fixed the parsers instead of loosening the validation limits, because quietly widening a guard to make a test pass is how a system becomes unsafe. I am likely to achieve my goal for the core: governed autonomy demonstrably works, live, end to end. Next I will commit two weeks of finished-but-untracked work, deploy the OSINT subsystem, and fix the one critical audit finding — a window where an approved action could theoretically fire twice — because provable correctness matters more than demonstrable features.

## PA3 — Making judgements and decisions

My most consequential decisions were all about restraint. First, the supervisor daemon that watches and nudges stuck tasks has *no* approve/reject code path at all — enforced by a method allowlist, pinned by tests, and mirrored by a server-side refusal of the "supervisor" actor — because an AI that can approve itself is not governed. Second, learning that my agent user could not write to the live install or restart services, I stopped fighting it and made the split a deliberate two-person rule: tested working copy, operator-run deploys. Third, when a read-only chat question once returned a raw source catalogue and falsely paused for approval, I rewrote the extraction contract to "the completed summary is the *only* user-facing content" — internal observations are context, never the answer. These decisions moved my learning forward because designing limits taught me more than designing features: I now think in failure modes, not demos. My next decision is whether to enable live OSINT collection and whether to commission an external security review before calling the system safe. Why: trust in a security tool must be earned from outside my own head.

## A2 — Appraising impact of strategies, perspectives and feedback

My most effective strategy has been the adversarial audit loop: at the end of each phase I task reviewer agents with a single mandate — break it — and every phase since late July has closed with a "confirmed findings" fix commit; my last full audit produced one critical, six high, sixteen medium and twenty-one low findings. What worked least was over-trusting my own tests: one used a fake connection that accepted a keyword the real API rejects, so the bug survived every green test and surfaced only live — the lesson, now recorded, is that mocks must mirror the real contract, not what my code wishes existed. Feedback has come from audits, failing tests, live behaviour, and re-reading my own documentation — which exposed stale counts and a two-week gap between my git history and reality. Different perspectives came deliberately: reviewers instructed to assume I am wrong, and reading my specs as a stranger. Feedback I could receive next: peer testing on real Windows machines, an external security review, first-time users of the client, and a teacher's reading of this reflection. Its impact on my goal has been to change what "done" means: no longer "it works", but "it fails loudly, its guarantees are pinned by tests, and its gaps are documented honestly" — the code states its one known rollback blind spot rather than hiding it. My next step is to close the critical finding and seek outside eyes, because the next stage of my learning is earning trustworthiness, not adding capability.
